雪花算法（Snowflake ID）

一个 64 位 long 拼出全局唯一 ID：41 位毫秒时间戳保趋势递增， 10 位机器号保多机不冲突，12 位序列号保单机同毫秒并发不冲突。 本地生成、无中心依赖、性能极高。

0164 位结构拆解

  • 1 位符号位：固定为 0，保证 ID 是正数
  • 41 位毫秒时间戳：当前毫秒 − 自定义起始纪元（如 2020-01-01），2⁴¹ ≈ 69 年不溢出；高位即时间 → ID 天然趋势递增，对 MySQL B+ 树索引最友好（顺序追加、无页分裂）
  • 10 位机器号：通常拆 5 位机房 ID + 5 位机器 ID，最多 1024 个节点；分配方式：手动配置 / Zookeeper / 数据库自增
  • 12 位序列号：同一毫秒内 0→4095 自增；单机理论上限 ≈ 409.6 万 QPS（4096 × 1000）

02优缺点

  • 优点：本地生成无网络开销（比 DB 自增、Redis INCR 都快）；趋势递增适合做 MySQL 主键；不依赖第三方组件，高可用
  • 缺点：依赖本地时钟 → 时钟回拨会发重复 ID（生产必须处理）；趋势递增意味着可枚举（竞争对手可估算你的订单量，对外暴露需加密/混淆）；机器号需要分配方案，否则扩容易冲突

03分布式 ID 方案对比（面试常考）

方案优点缺点
数据库自增 / 号段 实现简单、严格递增 依赖 DB 可用性；号段模式仍有单点风险
Redis INCR 性能不错、严格递增 多一个中间件依赖；持久化策略影响可靠性
UUID 无依赖、最简单 太长（36 字符）、无序 → 做 MySQL 主键引发频繁页分裂，性能差
雪花算法（本页） 无中心依赖、性能极高、趋势递增 时钟回拨需额外处理；机器号需分配
面试一句话：雪花 = 「41 位毫秒 + 10 位机器 + 12 位序列」拼成 64 位 long，本地生成、趋势递增、全局唯一；唯一要记住的坑是时钟回拨（等待 / 拒发 / 换机器号），以及分库分表场景下可把它和基因法结合（序列号低位嵌入分片基因）。
