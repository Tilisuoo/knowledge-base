MHA 架构实现 MySQL 高可用

主库半夜挂了，谁来顶？MHA = 一主两从 + Manager 哨兵： 主挂自动判定 → 选最新从库 + 补齐差异 binlog → 新主接管、从库改指向，全程 <30 秒、几乎不丢数据。

01大白话版（双 11 零点，master 断电了）

  • ① 平时：一主（10.0.0.1）两从（.2 / .3），master 每写一笔就通过 binlog 同步给从库；MHA Manager 像哨兵，每 3 秒 ping 一次主库；还可加一台 Binlog Server（可选）伪装成从库，把 binlog 实时再备份一份
  • ② 主挂了：零点 master 断电——Manager 连 ping 3 次（约 9 秒）都不通，判定死亡，自动开始 failover（故障切换）
  • ③ 选主 + 补数据：slave1 复制到 pos 4800、slave2 才 4500 → 数据最新的 slave1 上位；slave2 先向 slave1 要来 4500→4800 的差异日志补齐；旧主若还能 SSH 登录，连 4800→5000 的 binlog 也抢救回来
  • ④ 新主接管：slave1 升级为新 master 打开写入，slave2 改指新主，VIP 漂移到新主——全程 30 秒内，应用无感；旧主修好后降级为从库重新加入

02关键认知

  • MHA 的灵魂是「补数据」不是「选主」：选出最新的从库谁都会，难的是把差异补齐——从库间互比 relay log + SSH 抢救旧主残存 binlog，所以 MHA 几乎不丢数据，这是它区别于「裸切换」的核心卖点
  • 选主规则：默认比对各从库复制位置（master_log_pos），最新者优先；可用 candidate_master=1 指定优先候选（比如硬件更强的那台）
  • 常见误会①：MHA ≠ 读写分离 / 负载均衡——它只管「主库挂了自动切」，不管分流；读写分离是 ProxySQL / 中间件的活，两者常搭配出现但不是一回事
  • 常见误会②：MHA 不是多主架构——同一时刻只有一个可写主；防脑裂只靠「SSH 探测旧主 + 切换脚本」，极端网络分区下仍可能双主，这也是 MGR 后来居上的原因
  • 可选组件 Binlog Server：一台独立机器伪装成 slave，用 mysqlbinlog 流式实时拉取 master 的 binlog 存档（只存原始日志、不应用，相当于 binlog 仓库）——旧主彻底报废时，缺失的 binlog 也能从它那里补齐；不配它时，抢救数据的前提是「旧主还能 SSH」
  • Manager 是单点：但它挂了只是失去「自动切换」能力，业务读写完全不受影响（可双 Manager 或 Keepalived 兜底）
  • 现状：MHA 已停更多年（Perl 编写），新系统多用 MGR（组复制，Paxos 多数派、自带防脑裂）或 Orchestrator；但「binlog 补齐」的思想是相通的，MHA 仍是理解高可用切换的最佳样本

03高可用方案对比

方案切换速度数据安全特点
MHA（本方案） <30 秒 几乎零丢失（补 binlog） 成熟经典；Perl 编写、停更多年、防脑裂弱
MGR 组复制 秒级 多数派强一致 MySQL 官方方案；要求 InnoDB + GTID，网络开销略大
Orchestrator ~10 秒 依赖复制拓扑 拓扑可视化好；本身不补数据，常搭配 GTID + 半同步复制
手动切换 分钟 ~ 小时 看 DBA 水平和手速 半夜被叫起来的噩梦；只适合极小规模
面试一句话：MHA = Manager 哨兵 + 各机 Node——主库挂了自动选出数据最新的从库当新主，靠互比 relay log 和 SSH 抢救旧主 binlog 把差异补齐（几乎零丢数据），再让其他从库改指新主、VIP 漂移，全程 <30 秒。
