02读写路由时序

一次写请求 + 一次读请求的完整链路：代理层先解析 SQL 类型再决定路由目标；写结果返回客户端后，数据通过 Binlog 异步复制到从库（紫色虚线），对客户端完全透明。

  • 路由依据：SQL 类型（读 / 写）、事务状态（事务内强制走主库）、hint 强制指定
  • 负载均衡策略：轮询、加权轮询、随机、最少连接
  • 从库故障：自动摘除，读流量切换到其他健康从库
  • 主库故障：需配合 MHA / Orchestrator / MGR 做故障检测与选主切换
实现位置二选一：代理层集中路由（ProxySQL / MyCat），或客户端组件内嵌路由（ShardingSphere-JDBC），两者对比见第 4 节。

03关键问题：主从延迟

复制是异步的：主库写入成功后，从库需要一段时间才能追上。在延迟窗口内读从库会拿到旧数据——「刚下单却查不到订单」就是这个原因。

  • 强制读主：刚写入马上要读的场景（如下单后查订单）直接路由到主库，或用 hint 指定
  • 位点等待：读之前等待从库追到指定 GTID / binlog 位点（如 MySQL 8.0 的 WAIT_FOR_EXECUTED_GTID_SET）
  • 延迟剔除：监控 Seconds_Behind_Master，延迟超阈值的从库自动摘除
  • 缓存兜底：写成功的同时把新数据写入缓存，读请求先查缓存
  • 缩小窗口：半同步复制 + 从库并行回放（MTS），降低延迟与丢失风险
没有银弹：要强一致就读主库，接受最终一致就读从库——按业务对「读到旧值」的容忍度逐场景选择。

04两种实现方式对比

维度客户端封装（ShardingSphere-JDBC）服务端代理（ProxySQL / MyCat）
部署形态以 Jar 包嵌入应用，无额外组件独立部署的代理集群
性能少一跳网络转发，延迟更低多一跳代理转发
多语言支持仅 Java任意语言，对应用完全透明
运维成本配置随应用发布，升级需逐个发版集中管理、规则热更新；但需维护代理自身高可用
故障处理应用内感知，需自行集成健康检查代理统一做健康检查与故障摘除
适用场景Java 技术栈、追求低延迟、实例规模大多语言混合栈、希望统一管控数据库流量
一句话选型：Java 栈 + 大规模实例选客户端封装；多语言 / 统一治理选服务端代理；中小规模用 ProxySQL 起步最简单。
