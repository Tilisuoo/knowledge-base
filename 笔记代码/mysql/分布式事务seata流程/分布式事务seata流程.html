分布式事务 Seata 流程（AT 模式）

一次下单要动三个库，中间失败了怎么全部还原？—— TM 向 TC 领全局事务 XID → 一阶段：各分支直接提交 + 留 undo_log → 有失败则 TC 发全局回滚 → 照 undo_log 反向补偿，数据原样恢复。

01大白话版（买个手机壳，扣款失败了）

  • ① 开启：订单服务（TM）向 TC 领全局事务 XID=tx1001；XID 随调用链传给库存、账户服务
  • ② 一阶段：订单插单、库存 100→99 本地直接提交（各留一份 undo_log 回滚说明书）；账户扣款 100→90.1 失败：余额不足，本地回滚
  • ③ 判定：分支3 失败、异常抛回 TM → TM 拍板「全局回滚」发给 TC → TC 逐个通知各 RM 执行（全成功则 TM 发提交，TC 通知删 undo_log 收工，毫秒级）
  • ④ 回滚：分支1 照 undo_log 删掉订单 #1001、分支2 把库存 99 改回 100——数据原样恢复 ✓

02关键认知

  • AT 的灵魂：一阶段直接提交 + undo_log——对比传统 2PC「一阶段不提交、资源全锁干等」，Seata 用一份回滚日志换来高性能：二阶段提交＝删日志（快），回滚＝照 before image 反向补偿
  • before / after image 分工：回滚用 before 还原；after 用于回滚前校验——当前值 ≠ after 说明数据被别人动过（脏写），告警转人工处理，不能直接覆盖
  • 全局锁：一阶段本地提交前向 TC 申请（行级）——防止两个全局事务并发改同一行，把对方的 undo_log 写乱
  • 常见误会①：Seata AT 不是强一致——一阶段已提交，中间状态别人读得到（相当于读未提交）；要读已提交得 SELECT FOR UPDATE 走全局锁代理
  • 常见误会②：不是所有场景都能 AT——要求关系库 + undo_log 表 + 本地事务；调用外部接口等不支持的场景，用 TCC 模式手写三个方法
  • XID 怎么传：ThreadLocal 存放 + RPC 自动透传（Dubbo / Feign / MQ 均支持），业务代码零感知
  • 谁通知谁（指令链）：一阶段 RM → TC（注册分支 + 上报状态）；决议 TM → TC（发起全局提交/回滚）；二阶段 TC → RM（通知分支执行）。TM 是「拍板的」（业务 Owner），TC 是「传话 + 协调的」（登记所有分支），RM 是「干活的」
  • undo_log 存在哪：各业务库里（每个库建一张 undo_log 表），和业务 SQL 在同一个本地事务提交——「业务改了，回滚日志一定在」；TC 上只存事务状态 + 分支清单 + 全局锁，不扛数据快照。回滚时 TC 只带 XID + branch_id 通知，RM 自己去本地查 before image 生成反向 SQL

03Seata 四种模式对比

模式侵入性一致性性能适用场景
AT（本图） 无侵入 最终一致 高（一阶段即提交） 关系库常规业务，90% 场景首选
TCC 高（手写 Try / Confirm / Cancel） 最终一致 高（不锁资源） 资金、积分等核心场景，或调外部接口
Saga 中（状态机编排） 最终一致 高 长流程：跨公司、老系统、数天跨度
XA 无侵入（依赖 DB 支持） 强一致 低（资源全程锁定） 强一致刚需（银行核心账务）
面试一句话：Seata AT = TC 协调 + TM 发起 + RM 管分支——一阶段业务 SQL 直接提交、只留 undo_log（before / after image），全成功则二阶段删日志收工，有失败则照 before image 反向补偿；用「一阶段早提交」换高性能，代价是最终一致。
