分库分表查询（多维路由）

分片键只有 buyer_id 一个，其他维度怎么查？ ① 买家查走分片键；② 订单号查用基因法； ③ 卖家查冗余双写一份；④ 运营多维查交给搜索平台。

01数据流（淘宝订单方案）

  • 下单写：订单号 = 雪花 ID + 买家基因（buyer_id % 2 编进 id 低位）→ 订单 MQ → 双写买家库、卖家库
  • ① 买家查：WHERE 带 buyer_id → % 2 算分片 → 买家库单片场
  • ② 订单号查：解析 id 低位基因 → 买家库同一片，不需要知道 buyer_id
  • ③ 卖家查：WHERE 带 shop_id → 卖家库单片场（同一份数据，按卖家维度重新分片布局）
  • ④ 运营多维查：binlog 同步到搜索平台（ES），任意字段组合查询，不打交易库
  • 取舍逻辑：高频主路径 → 冗余副本一次到位；低频多维 → 搜索兜底；系统生成的 id → 基因法零成本路由

02非分片键查询 · 方案全景

方案原理适用代价
分片键查询 WHERE 带分片键，中间件 % N 直接路由单片场 一切高频查询的前提（买家查订单） 无 —— 分片键选对了就是免费的
基因法 生成 id 时把分片键基因编进低位，id % N 直接算分片 系统生成的值：订单号、流水号（客服查单） ID 生成器自研；基因位数锁死分片数上限
冗余双写 同一份数据按另一维度再分片存一份（卖家库） 另一条高频主路径（卖家查订单） 双倍存储 + MQ 双写最终一致性
映射表 维护「字段值 → 分片键」映射（DB + Redis 缓存） 高基数点查字段：手机号、邮箱查单 多一跳 KV；映射一致性维护
广播归并 中间件把 SQL 广播到所有分片，结果内存归并 低频、小结果集（后台偶尔查一次） 分片越多越慢；深分页归并内存爆炸
ES 异构 binlog → Canal/MQ → Elasticsearch 多维组合、模糊查询（运营/客服后台） 同步链路复杂度；秒级延迟
一句话选型：查询必带分片键是免费的，其他维度全是「花钱买路由」——能算（基因法）就不查（映射表），高频就冗余（双写），低频就凑合（广播），多维组合交给 ES。
