分库分表（水平拆分）

① 写请求按分片键路由到目标分片的主库；② 读请求路由到分片从库； ③ 每个分片内部仍是一套独立的一主一从复制。

01数据流

  • ① 写请求：携带分片键（如 user_id），中间件按路由规则 user_id % 2 算出目标分片，写入该片主库——同一用户的数据永远落在同一片
  • ② 读请求：同样按分片键路由到对应分片的从库；没带分片键的查询会被广播到所有分片、结果归并后返回（慢，要尽量避免）
  • ③ 片内复制：每个分片仍是一套独立的一主一从，Binlog 复制保证片内高可用与读扩展
  • 片内还可再分表：库路由 user_id % 2、表路由 order_id % 2，落到 order_0 / order_1

02两种拆分方式

方式怎么拆解决什么局限 / 代价
垂直拆分 按业务拆库：用户库 / 订单库 / 商品库各自独立 业务解耦、单库连接数与容量压力 单表数据量大了依然扛不住
水平拆分（本图） 同一张表按分片键把行分散到多片：order_0 / order_1 … 单表千万级+ 的数据量与写入瓶颈 跨片 JOIN / 分布式事务 / 结果归并变复杂

03特点

  • 优点：突破单库容量与写入瓶颈，加机器即可近线性水平扩展；分片之间故障隔离
  • 缺点：跨片 JOIN / 分布式事务（XA、Seata）复杂；需要分布式全局 ID（雪花算法、号段模式）；跨片分页排序要归并；扩容需数据迁移（翻倍扩容 / 一致性哈希）
  • 适用：单表千万级以上、主库写满、读写分离也扛不住的大型业务
核心权衡：分库分表是「最后的手段」——先用 读写分离扛；非拆不可时先垂直拆（按业务），还不够再水平拆（按分片键）。拆分之后，「数据永远跟着分片键走」是设计第一原则。
