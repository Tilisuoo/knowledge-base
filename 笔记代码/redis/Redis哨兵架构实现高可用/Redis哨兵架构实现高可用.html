Redis 哨兵架构实现高可用

master 挂了，一群哨兵投票说了算：一主两从 + 3 哨兵盯梢 → 主观下线 → quorum 投票客观下线 → 选 Leader 哨兵 → 挑 offset 最新的从库 → 新主接管，客户端问哨兵要地址。

01大白话版（零点，master 断电了）

  • ① 平时：一主（10.0.0.1）两从（.2 / .3）实时同步；3 个哨兵一起盯梢——单个哨兵可能自己网络抖动误判，所以用一群（quorum=2）
  • ② 主挂了：S1 发现 ping 超 30 秒不通（主观下线：我觉得挂了）；赶紧问 S2/S3，3 票里 2 票同意（客观下线）→ 真挂了，开切
  • ③ 选 Leader + 选新主：哨兵内部先投票选「话事人」（S2 得 2 票当选）；话事人按规则挑新主——剔除下线的 → 比 slave-priority → 比 offset（4800 > 4500，slave1 上位）→ 比 run ID
  • ④ 新主接管：slave1 执行 SLAVEOF NO ONE 升主，slave2 改指新主；客户端问哨兵拿到新地址直连；旧主修好后被降级为从库

02关键认知

  • 为什么要「主观 → 客观」两段判定：单个哨兵可能因自己网络抖动误判 master 死亡；quorum 个哨兵都同意才算客观下线，把误判概率压到最低（quorum 一般配成哨兵总数的多数派）
  • 谁来执行 failover：不是全体一拥而上——哨兵先 Raft 式投票选出 Leader Sentinel（得票 ≥ max(quorum, 多数派)），由它一个人执行，避免并发切换出乱子
  • 选新主的顺序规则：① 剔除下线/断连超时的 slave → ② slave-priority 小的优先（配 0 = 永不选）→ ③ 复制 offset 大的优先（数据最新）→ ④ run ID 字典序兜底
  • 常见误会①：哨兵 ≠ 一个进程——生产至少 3 个、奇数、跨机器部署；单哨兵自己就是单点，还无法形成多数派
  • 常见误会②：哨兵不能根治脑裂——网络分区时旧主可能还在收写。缓解靠 min-replicas-to-write 1 + min-replicas-max-lag 10：主发现连不上足够从库就拒写，宁可不可用也不多写
  • 客户端怎么找到新主：问任一哨兵「当前 master 地址」，或订阅 +switch-master 事件——所以客户端要接 Sentinel，而不是写死 IP
  • 和 MHA 的本质区别：MHA 是「一个裁判自判 + SSH 抢救 binlog」；哨兵是「一群裁判投票 + 选 offset 最新者」，不抢救旧主数据

客户端寻址 问哨兵 / 订阅事件 VIP 漂移（脚本） 槽位跳转（MOVED）
面试一句话：Redis 哨兵 = 一组哨兵进程（≥3、奇数、跨机器）盯主从——master 挂了先「主观下线」、quorum 投票「客观下线」，哨兵再选出 Leader，把 offset 最新的从库升为新主、其余改指，客户端向哨兵要新地址；配 min-replicas-to-write 缓解脑裂。
