尾部热点（Tail Hotspot）

按自增 ID 或时间顺序追加数据时，所有写入都砸在「尾部」的最后一个分片上—— 前面的分片都闲着，负载全部集中在尾部，分片集群被退化成单机。

01什么是尾部热点

  • 定义：数据按自增 ID 或时间顺序追加写入，而分片按范围（Range）划分——最新的数据永远落在「最大区间」的最后一个分片上，写入压力全部集中在尾部，前面的分片完全闲置
  • 后果：分片集群被退化成单机——N 台机器只有 1 台在干活，写入瓶颈一点没解决；尾部那台被打满时，整体写入还是会崩
  • 对照：换成哈希取模分片，连续 ID 被打散轮流落到各片，负载均匀——但代价是范围查询全废（见分库分表的取舍）

02典型场景

场景尾部热点是怎么来的
日志 / 流水表按时间范围分片 按月分片（2026-01 → 片 0，2026-02 → 片 1…）：当前月的写入永远全压最新那一片，历史月份只读不写
按自增 ID 范围分片 id 1~1000万 → 片 0，1000万~2000万 → 片 1…：新插入 id 只涨不降，永远写尾部
MongoDB 用自增/时间字段做片键 chunk 按片键范围划分，自增片键导致所有 insert 进最大 chunk，触发不停的分裂与迁移
Kafka 消息按时间戳哈希分区 所有消息进同一分区，消费端也只能单线程消费，吞吐上不去

03解决办法

  • ① 换哈希分片（最常用）：分片键改成 hash(user_id) % N 或 user_id % N，写入天然打散；范围查询需求交给 ES / 数仓
  • ② 分片键加盐（Salted Key）：既要时间有序又要打散——用 hash(时间戳 + 随机后缀) 或 时间戳 + hash(id) % K 做片键，把同一时间段的数据撒到 K 个分片，牺牲部分范围查询效率换负载均衡
  • ③ 预分桶（Pre-split）：建表时就把尾部分片拆成多个小桶，写入被分摊到多个桶（MongoDB 预分 chunk、HBase 预分区都是这个思路）
  • ④ 业务层错峰：日志/统计类写入先落 MQ 缓冲，消费端均匀写入各分片，削掉瞬时尖峰
面试一句话：尾部热点 = 「写入有顺序 + 分片按范围」的必然结果，新数据全压最后一片；解法是哈希打散（首选）、分片键加盐或预分桶——用范围查询能力换负载均衡。
