Canal + MQ 异构数据同步

MySQL 改了价，ES 和 MongoDB 怎么跟着变？—— Canal 伪装从库白拿 binlog → MQ 广播消息 → 下游各自订阅消费 → 异构存储最终一致，业务表全程零侵入。

01大白话版（跟着一次改价走完全程）

  • ① Canal 监听：MySQL 本来就会把 binlog（所有增删改的流水账）同步给从库——Canal 假装自己是从库，主库就主动发它一份。例：运营把「iPhone 15 手机壳」从 19.9 改成 9.9，这条 UPDATE 立刻进 binlog，Canal 秒级拿到
  • ② 投递 MQ：Canal 把 binlog 翻译成 JSON 消息丢进 MQ（公告栏）；它不关心谁来拿、有几个下游——发完就走
  • ③ 订阅消费：团队B 的 ES 拿消息更新搜索索引（搜「手机壳」看到 9.9），团队C 的 MongoDB 更新详情文档（详情页显示 9.9）——同一条消息，各存各的模型，互不认识
  • ④ 最终一致：全链路异步，有秒级延迟——不保证这一秒三边相等，保证很快都变成 9.9

02关键认知

  • Canal 原理 = 白嫖主从复制：伪装 slave 向 master 发起 dump 协议，binlog 一产生就推过来——业务表零侵入、零 SELECT 负载、实时性高，且增删改一条不漏（轮询查不到「已删除」的行）
  • 为什么中间夹一层 MQ：解耦（团队A 不认识 B/C，新增下游零改动）、削峰（大促改价洪峰排队慢慢消费）、可重放（下游宕机恢复后补消费）；Canal 也支持直发 ES/Kafka，但多方订阅场景 MQ 是标配
  • 常见误会①：Canal ≠ 定时轮询查表（SELECT ... WHERE update_time > x）——轮询延迟高（分钟级）、扫表有负载、抓不到物理删除的行
  • 常见误会②：这是最终一致不是强一致——「下单扣库存」这种强一致读取必须走 MySQL 主库，别读 ES/MongoDB
  • 工程坑：同一行的多次变更要按主键 hash 分区保序消费（不然 9.9 可能被旧的 19.9 覆盖）；消费端做幂等（消息可能重复投递）

03方案对比

方案实时性侵入性说明
Canal + MQ（本方案） 秒级 零侵入 主流标配；链路长，要运维 Canal + MQ
定时轮询 update_time 分钟级 零侵入 实现最简单；扫表有负载、抓不到物理删除、要求表有 update_time 字段
业务代码双写 毫秒级 侵入代码 写 ES 失败即不一致，要本地消息表 / 事务补偿兜底
云服务 DTS / Debezium 秒级 零侵入 同款 binlog 原理，开箱即用 / 生态成熟；厂商绑定或自建运维成本
面试一句话：Canal 伪装成 MySQL 从库订阅 binlog，把增删改解析成消息投进 MQ，ES、MongoDB 等下游各自订阅消费——业务表零侵入，换来异构存储的最终一致（秒级延迟）。
